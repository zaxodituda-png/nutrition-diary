# Дневник питания: PHP + MySQL / MariaDB

Эта ветка готовит перенос с GitHub Pages на обычный PHP-хостинг. Она ничего не развёртывает и не меняет существующие записи браузера. GitHub Pages не исполняет PHP; до завершения переноса оставьте старый сайт и его данные доступными.

Интерфейс, календарь, расчёт калорий, сравнение веса с предыдущей **доступной пользователю** записью и Garmin сохранены. В новой версии основное хранилище — база данных. Только администратор изменяет записи. Посетители читают только опубликованные записи; черновики видит администратор. Если предыдущий вес есть только в черновике, посетитель его не получает и сравнение строится по опубликованным данным.

## Что потребуется от хостинга

- PHP **8.2+**, предпочтительно поддерживаемый PHP 8.4+, расширения `PDO`, `pdo_mysql`, `session`, `json`; поддержка `random_bytes`, `password_hash`, `password_verify`. Composer и Node.js для работы сайта не нужны.
- MySQL **5.7+** или MariaDB **10.3+**, InnoDB, кодировка `utf8mb4`. Проверено на PHP 8.4 и MariaDB 11.8. Для нового сервера выбирайте поддерживаемую поставщиком версию БД.
- HTTPS с действительным сертификатом и перенаправление HTTP → HTTPS. PHP должен видеть `$_SERVER['HTTPS'] = 'on'`/`1`. Если TLS завершает nginx, ISPmanager/хостер должен правильно передавать этот признак в PHP-FPM. Приложение **не доверяет** присланному посетителем `X-Forwarded-Proto`.
- Возможность назначить корнем сайта папку `public/` либо разместить `private/` вне существующего веб-корня и изменить путь подключения (ниже). Секреты нельзя защищать только `.htaccess`.
- Изолированное от других аккаунтов, доступное PHP для записи хранилище сессий. В PHP включить `session.use_strict_mode=1`, `session.use_only_cookies=1`, `display_errors=Off`, `log_errors=On`. Логи должны храниться вне веб-корня.
- Apache с `.htaccess`, `mod_headers`, разрешённым `Options -Indexes`; или эквивалентные настройки nginx у хостера. Для nginx `.htaccess` не работает: явно отключите листинг, запретите доступ к закрытым каталогам, передайте PHP в FPM и добавьте заголовки из `public/.htaccess`.
- Для JSON-импорта `post_max_size` не меньше **16M**, лимит тела запроса nginx/Apache не меньше **16 MB**, `memory_limit` от **128M**. Приложение принимает до 10 MiB JSON на запрос, до 5000 дат и до 128 KiB на запись. Для больших архивов делите файл на несколько объектов по датам; исходник сохраняйте.
- Виртуальный хост должен пропускать заголовок `X-CSRF-Token`, не добавлять CORS и не кэшировать `api/`. Для API обязателен `Cache-Control: no-store, private`.
- Соединение с Garmin идёт из браузера посетителя; на PHP-сервере не нужны внешние HTTP-запросы, Strava API или дополнительные ключи.

## Структура проекта

```text
nutrition-diary/
  public/                 <-- единственный веб-корень
    index.html, app.js, styles.css
    api/index.php
    setup.html, setup.js   <-- однократная настройка, без секретов в файлах
    .htaccess
  private/                <-- вне всех публичных каталогов и алиасов
    config.example.php    <-- пустой шаблон; config.php создаётся только на сервере
    bootstrap.php
    migrations/001_initial.sql
    bin/migrate.php
    bin/setup-token.php
    bin/reset-password.php
    legacy-example.json   <-- прежняя демонстрационная запись, НЕ импортируется автоматически
  tools/                  <-- локальные инструменты; в веб-корень не загружать
  tests/                  <-- тесты; в веб-корень не загружать
```

`private/config.php`, выгрузки БД, логи, реальные JSON-архивы и пароли не коммитить. `.gitignore` исключает конфигурацию, но перед каждым коммитом всё равно проверяйте список файлов. Исходная демонстрационная запись сохранена отдельно, а не удалена и не опубликована сервером автоматически.

## Развёртывание в ISPmanager — вручную, когда будете готовы

1. **Сначала экспортируйте старые записи** по инструкции ниже и сделайте резервную копию файлов текущего сайта. Если база уже существует — сделайте и SQL-дамп. Не отключайте GitHub Pages и не очищайте localStorage до сверки переноса. Реальные локальные записи не хранятся в GitHub, поэтому одного скачивания репозитория недостаточно.
2. Скачайте ZIP этой ветки GitHub. В ISPmanager откройте **Сайты / WWW-домены → Создать** (названия зависят от версии панели). Выберите домен, PHP-FPM/CGI с PHP 8.2+, включите SSL и перенаправление на HTTPS. Выпустите сертификат Let's Encrypt либо установите сертификат хостинга.
3. Через **Менеджер файлов** или SFTP загрузите структуру проекта, например:
   `/var/www/USER/data/www/diary.example.com/public/` и соседнюю `/var/www/USER/data/www/diary.example.com/private/`.
   В свойствах сайта назначьте **корневой каталог** `/www/diary.example.com/public` (или абсолютный эквивалент панели). Домен должен открывать только `public/`, не родительский каталог.
   Не загружайте `.git`, `tests/`, `tools/`, JSON-резервные копии в веб-корень. Если панель не позволяет изменить корень, загрузите **содержимое** `public/` в назначенный корень, а `private/` — например, в `/var/www/USER/data/nutrition-diary-private/`, вне всех сайтов. В `api/index.php` замените единственную строку `require dirname(__DIR__, 2) . '/private/bootstrap.php';` на `require '/var/www/USER/data/nutrition-diary-private/bootstrap.php';`. Пути CLI в дальнейших командах также скорректируйте.
4. В **Базы данных → Создать** заведите отдельную БД и пользователя с уникальным паролем. Запишите реальные имя БД, имя пользователя, пароль, хост и порт из панели. Не используйте административный/root-аккаунт MySQL. При создании таблиц нужны `CREATE`/`INDEX` (для последующих миграций — `ALTER`); после настройки оставьте runtime-пользователю только `SELECT`, `INSERT`, `UPDATE`, `DELETE` на этой БД. Если панель не разделяет права, используйте отдельного миграционного пользователя вручную через phpMyAdmin и храните в конфигурации только ограниченного runtime-пользователя.
5. В закрытом `private/` скопируйте `config.example.php` в `config.php` и заполните:
   - `site_url`: точный HTTPS-адрес, например `https://diary.example.com` или `https://example.com/diary` для подпапки; без завершающего `/`.
   - `db.host`, `db.port`, `db.name`, `db.user`, `db.password`: значения из ISPmanager. Поддерживается локальное/доверенное соединение БД; для удалённой БД требуется защищённая сеть/настройка TLS у хостера.
   - `allow_http_localhost`: оставить `false`.
   - `setup_token_hash`: пока пустая строка; следующий раздел объясняет настройку.
   Дайте файлу права `600` или `640` с правильным владельцем/группой PHP, закрытому каталогу — `700` или `750`. PHP должен иметь право читать файл. Никогда не используйте `777`.
6. Создайте таблицы **одним** из способов:
   - Терминал/SSH ISPmanager: `php /ABSOLUTE/PATH/private/bin/migrate.php`. Убедитесь, что `php -v` показывает нужную версию и CLI имеет `pdo_mysql`. Скрипт повторяемый, без `DROP`/`TRUNCATE`, сериализует миграции блокировкой БД.
   - Без SSH: откройте **phpMyAdmin** из ISPmanager, выберите нужную БД и импортируйте `private/migrations/001_initial.sql`. Он также повторяемый. Будущие нумерованные SQL-файлы применяйте по порядку, предварительно сделав SQL-дамп. Миграции добавляют схему, но **не** дневниковые записи.
7. Создайте первого администратора по следующему разделу, затем войдите на сайт и импортируйте JSON. Каждый импорт добавляет **черновики**. Проверьте даты, вес, продукты, калории и Garmin; для каждой нужной записи включите «Опубликовать запись для посетителей» и сохраните.
8. Проверьте в отдельном браузере/приватном окне: видны только опубликованные даты, кнопок редактирования нет; прямые POST к `api/index.php?action=save`, `delete`, `import` без авторизации возвращают `401`/`403`. Экспорт базы без входа также запрещён. На `api/index.php?action=session` не должно быть PHP-кода, HTML-ошибки или SQL-реквизитов в ответе.
9. Проверьте, что URL `/private/config.php`, `/config.php`, `/tests/`, `/.git/config` недоступны и не отдают содержимое файлов, а API не кэшируется. В инструментах браузера убедитесь, что cookie `nutrition_admin` имеет **Secure, HttpOnly, SameSite=Strict**. При HTTP приложение не должно позволять вход; проверьте перенаправление на HTTPS. Для nginx попросите хостера перенести заголовки безопасности из `.htaccess` в конфигурацию сайта.
10. После сверки количества дат/полей и сохранения локального JSON/SQL-бэкапа можно менять DNS/ссылку для нутрициолога. Для сохранения конфиденциальности удалите старую публичную демонстрацию/отключите GitHub Pages отдельно, когда решите: этот код не управляет прежним хостингом и не стирает его данные.

## Первый администратор: без стандартного логина и пароля

В приложении нет предустановленного администратора и нет открытой регистрации.

1. Сгенерируйте **новый случайный токен** одним из двух способов:
   - В терминале: `php private/bin/setup-token.php` (на сервере либо локально). Он выводит 64-символьный одноразовый токен и его SHA-256.
   - Без PHP/SSH: откройте скачанный `tools/generate-setup-token.html` **локально** на своём компьютере. Он генерирует токен средствами браузера без сети и показывает SHA-256. Не загружайте инструмент на хостинг и не используйте сторонние сайты для обработки токена.
2. Сохраните сам токен временно в менеджере паролей. Вставьте **только его SHA-256** в `setup_token_hash` закрытого `private/config.php`. Не отправляйте токен в URL, GitHub, чат, почту или логи.
3. Откройте `https://ВАШ-ДОМЕН/setup.html` (или `/diary/setup.html` для подпапки). Введите токен, придумайте логин (3–64 латинских буквы/цифры/`_.-`) и сильный уникальный пароль **12–72 байта**. Для кириллицы байт больше, чем символов. Используйте менеджер паролей. Форма отправляет JSON по HTTPS с CSRF-токеном; пароль хранится только как `password_hash(PASSWORD_DEFAULT)`.
4. Создание администратора блокируется в транзакции: только один первый администратор, повторная настройка запрещена даже при сохранённом токене. После успеха очистите `setup_token_hash` до `''`, удалите с хостинга `public/setup.html` и `public/setup.js` и удалите временный токен. Отключение настройки обязательно выполните вручную; runtime-пользователь PHP не должен переписывать конфигурацию.
5. Войдите через «Вход администратора». Сессия обновляет идентификатор после входа, действует до 30 минут бездействия и не более 8 часов. На общем компьютере нажимайте «Выйти».

При потере пароля используйте закрытый CLI `private/bin/reset-password.php USERNAME`: пароль читается со **стандартного ввода**, а не из аргумента команды. Например, в Bash терминала ISPmanager:

```bash
read -r -s -p 'Новый пароль: ' diary_new_password
printf '\n'
printf '%s' "$diary_new_password" | php /ABSOLUTE/PATH/private/bin/reset-password.php YOUR_USERNAME
unset diary_new_password
```

Смена хэша отзывает прежние сессии при следующем запросе API. При отсутствии SSH обратитесь в поддержку хостинга для запуска CLI; повторно включать первичную настройку или редактировать `setup_state` не нужно.

## Перенос существующих localStorage-записей

**localStorage привязан к origin (протокол + домен + порт) и браузерному профилю. Новый домен не может прочитать данные GitHub Pages. Не очищайте браузер и не переименовывайте старый ключ.**

### Экспорт со старого адреса

1. Откройте старый сайт `https://zaxodituda-png.github.io/nutrition-diary/` в том браузере/профиле, где вводили записи. Для локальной версии откройте прежний `index.html` тем же способом, которым пользовались раньше; доступ к localStorage у `file://` зависит от браузера.
2. Откройте DevTools → Console. Просмотрите и выполните код из `tools/export-legacy.js`: он только читает `nutrition-diary-v1` и скачивает JSON, ничего не удаляет и не отправляет в сеть. Полный код:

```javascript
(()=>{
  const raw=localStorage.getItem('nutrition-diary-v1');
  if(raw===null)throw new Error('На этом адресе/в этом профиле нет сохранённых записей.');
  JSON.parse(raw);
  const url=URL.createObjectURL(new Blob([raw],{type:'application/json'}));
  const link=document.createElement('a');
  link.href=url;link.download='nutrition-diary-legacy.json';link.click();
  setTimeout(()=>URL.revokeObjectURL(url),1000);
})();
```

3. Храните файл локально как резервную копию, не загружайте его в публичный репозиторий. Повторите экспорт для других браузеров/устройств — у них могли быть разные записи.
4. Если localStorage пуст, прежний сайт мог показывать только демонстрационную запись без фактического сохранения. Оригинальная демонстрация сохранена в `private/legacy-example.json`; при необходимости импортируйте её вручную. Не подменяйте ею реальную резервную копию.

Кнопка «Экспорт старых записей этого браузера» в новой версии помогает только для данных **того же origin**, например при переносе сайта на PHP без смены домена. Она не выдаёт данные за серверные и ничего не удаляет.

### Импорт на новый сервер

1. Авторизуйтесь, нажмите «Импорт JSON» и выберите файл. Принимается старый объект `{ "YYYY-MM-DD": { ...поля записи... } }` либо новый экспорт `{ "format": "nutrition-diary", "version": 1, "entries": { ... }, "published": { ... } }`.
2. Подтвердите добавление черновиков. Все записи валидируются до записи, затем импортируются в одной транзакции. Существующие даты (включая мягко удалённые) **пропускаются**, не заменяются и не объединяются автоматически. Результат перечисляет пропущенные даты. Это позволяет повторить импорт без дубликатов.
3. Импорт сохраняет старые дополнительные поля, включая скрытые значения прежних ручных метрик и старый activity-link. Garmin в старом поле `strava` продолжает распознаваться, Strava-карточки не возвращаются. При следующем сохранении используется новое поле `garmin`.
4. Импорт всегда создаёт черновики, даже если JSON содержит `published: true`. Проверьте и публикуйте записи осознанно. Если несколько файлов содержат **разные** записи одной даты, сначала сохраните все исходники, затем вручную сверьте данные этой даты в редакторе: автоматической перезаписи нет.
5. «Экспорт базы в JSON» доступен только администратору, включает все **активные** записи/черновики и их статусы публикации. Его повторный импорт также не заменяет существующие даты. Для полного аварийного восстановления, включая удалённые записи, историю и учётную запись, используйте **SQL-дамп** базы, а не JSON.

## Хранение и защита данных

- PDO с настоящими prepared statements; параметры запросов не подставляются в SQL-строки.
- Доступ к изменению проверяется в PHP на каждом запросе, независимо от скрытых кнопок. База экспортируется только после входа. API не выдаёт черновики посетителям.
- Все изменения, вход, выход и первичная настройка: POST JSON + сессионный `X-CSRF-Token`, проверка `Origin` при наличии, без CORS; cookie HttpOnly/Secure/SameSite=Strict. Ограничение входа/настройки: не более 10 запросов с одного IP за 15 минут, хранится в БД и не сбрасывается новой сессией. За общим NAT/IP лимит общий; не доверяем присланному `X-Forwarded-For`.
- Данные выводятся как экранированный текст. Garmin URL/iframe разбираются только для извлечения числового ID с точного домена `connect.garmin.com`; произвольный HTML не вставляется. Встраивается `/modern/activity/embed/ID`, не страница активности. Garmin может блокировать карточку/требовать публичность; ссылка «Открыть в Garmin Connect» остаётся всегда, автоматического обещания успешного встраивания нет.
- Записи хранятся по дате в JSON-поле LONGTEXT для совместимости MySQL/MariaDB и сохранения прежних полей. Дата, размер, строки, продукты и числовые калории проверяются сервером. Вычисления выполняются прежним интерфейсом из серверных данных.
- У редактора есть проверка версии. Устаревшее сохранение получает `409`, не заменяет более новую запись; несохранённые поля остаются в форме. Скопируйте их, обновите страницу и сравните изменения перед повторным сохранением. Смена даты в редакторе сохраняет копию на новую дату, как в старом приложении; прежняя дата не удаляется.
- Редактирование записывает прежнее состояние в `entry_history`, удаление — мягкое (`deleted_at`), с архивированием. Удалённая запись исчезает из интерфейса, но её данные не стираются. Повторное создание/импорт той же удалённой даты заблокированы, чтобы не затереть её; восстановление выполняется администратором БД после резервного копирования. В SQL-восстановлении очистите `deleted_at`, оставьте `published=0` и увеличьте `revision`; при выборе старой версии скопируйте нужный `payload` из истории. Публичного endpoint восстановления нет.
- Публичные записи доступны всем, кто знает адрес. Эта версия не добавляет отдельную закрытую учётную запись нутрициолога: не публикуйте данные, которые не должны быть доступны посетителям.
- Регулярно делайте SQL-дамп через ISPmanager и резервную копию закрытого `config.php`; храните их отдельно от сайта с ограниченным доступом. Включите расписание резервных копий в панели. Код не удаляет прежнее localStorage и не синхронизирует его обратно.

## Проверка перед переключением домена

1. Вход/выход; посетитель не может вызвать запись/удаление/импорт/экспорт напрямую. Запрос администратора без CSRF → `403`; неверный пароль → `401`; превышение лимита → `429`.
2. Создание черновика, публикация, правка, удаление; две вкладки не перезаписывают изменения друг друга. Перезагрузка и другой браузер получают одну базу данных.
3. Калории продуктов, базовый и тренировочный расход, дефицит/профицит, календарь и сравнение веса (включая пропуски/невалидные веса).
4. Старый JSON импортируется; повторный импорт ничего не заменяет; файл с ошибкой не импортируется частично; исходное localStorage остаётся. Экспорт базы содержит ожидаемые активные даты.
5. Garmin: оба URL `/modern/activity/ID` и `/modern/activity/embed/ID`; при недоступной карточке ссылка работает. Не считайте HTTP 200 iframe доказательством, что Garmin действительно показал активность.
6. Права файлов, HTTPS, cookie, заголовки и доступность приватных путей — именно на вашем Apache/nginx/PHP-FPM. Локальные тесты не заменяют эту проверку конфигурации хостинга.

## Тесты разработки

Тесты **только на отдельной пустой тестовой БД**, никогда на базе с реальными записями. `tests/api.py` создаёт администратора, тестовые записи, меняет и мягко удаляет их.

1. Создайте отдельную БД/пользователя, локальный `private/config.php` с `site_url = http://127.0.0.1:8780`, `allow_http_localhost = true`, заполните случайный `setup_token_hash` и примените миграцию дважды для проверки повторяемости.
2. Запустите `php -S 127.0.0.1:8780 -t public`. В продакшене встроенный сервер PHP не используется.
3. Задайте в окружении `DIARY_TEST_URL`, `DIARY_TEST_SETUP_TOKEN`, `DIARY_TEST_PASSWORD` (уникальный пароль 12–72 байта) и запустите `python3 tests/api.py`.
4. API-тест исчерпывает лимит входа. Только в тестовой БД очистите `auth_limits` через SQL, затем запустите `node tests/browser.cjs` с Playwright и Chromium; `CHROMIUM_PATH` задаёт исполняемый файл. Браузерный тест ожидает состояние после API-теста. Production Node.js не требуется.
5. PHP lint: `find public private -name '*.php' -exec php -l {} \;`; JS: `node --check public/app.js` и `node --check public/setup.js`.

Проверено локально на PHP 8.4.24 + MariaDB 11.8.6: повторная миграция схемы, первичная настройка/запрет повтора, аутентификация, смена ID сессии, CSRF/Origin/методы, запрет записи/экспорта посетителям, черновики, конфликты версий, импорт без перезаписи/частичного применения, JSON-экспорт, мягкое удаление, лимит входа; Chromium — сохранение/перезагрузка, XSS-экранирование, приоритет БД над localStorage, расчёты/вес/календарь, Garmin и мобильная ширина. Реальная доступность карточки Garmin зависит от сервиса и настроек вашей активности.

## Начало дневника: 7 ноября 2026 года

В календаре все даты до `2026-11-07` серые и недоступны для выбора, включая предыдущие месяцы и годы. Навигация по месяцам сохраняется. Дата в редакторе ограничена тем же минимумом; сервер отклоняет сохранение, удаление и импорт более ранних дат с HTTP 422, независимо от интерфейса. Импорт файла с такой датой отклоняется целиком до изменений БД: сохраните исходный архив, для импорта выделите записи с 7 ноября и позже в отдельный JSON. Уже существующие ранние данные не удаляются и не переписываются, остаются в экспорте и учитываются прежним алгоритмом сравнения веса, но в календаре их нельзя выбрать или отредактировать.

Небольшая точка обозначает только опубликованную запись, в том числе при входе администратора. Черновики и пустые даты не получают точку. Тёмная заливка выделяет выбранную доступную дату; точка остаётся отдельным признаком публикации.

Дополнительный браузерный тест: `node tests/calendar.cjs` после API-тестов на отдельной тестовой БД (предварительно очистить тестовый `auth_limits`). Он проверяет ноябрьскую границу, переходы по месяцам и годам, клики/клавиатуру, точки опубликованных записей/черновиков, минимум редактора и программную попытку обойти его. Настройки хостинга и схема БД не меняются.
