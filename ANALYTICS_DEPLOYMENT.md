# Семидневная аналитика: проверка и ручное обновление REG.RU

Изменения подготовлены для существующей PHP/MySQL-версии. Слияние PR не обновляет production. Развёртывание не выполнялось.

## Что изменилось

Постоянный блок «Последние 7 дней» расположен между календарём и отчётом. Период — сегодняшняя локальная дата и шесть предыдущих календарных дней, независимо от выбранного отчёта. При переходе через местную полночь/возвращении к вкладке период обновляется, выбор отчёта сохраняется. Первый выбор календаря — сегодня, но не ранее 07.11.2026. Локальная дата определяется через getFullYear/getMonth/getDate, без UTC-сдвига; арифметика уже определённых календарных дат учитывает границы месяцев/лет.

Шесть переключателей управляют одним графиком. Единственное новое значение localStorage — идентификатор выбранной метрики; данные дневника туда не записываются. При запрете localStorage переключение работает без сохранения предпочтения. График поддерживает мышь, касание и стрелки клавиатуры, показывает точную дату/значение, не соединяет пропуски и различает отсутствующие значения и нули. Отрицательный дефицит — профицит. Оси масштабируются по данным независимо от указателя.

Всегда видимое «Общее» использует тот же период:

- Дистанция: сумма сохранённых FIT summary.distanceKm.
- Время тренировок: сумма summary.movingSeconds только формата v2. Старые v1 не подменяются elapsed time; их дистанция доступна, время отсутствует до повторного импорта FIT.
- Дефицит: сумма подписанных base + exercise − sum(meal.kcal), как в отчёте.
- Активные ккал: сумма exercise.
- Вес: среднее валидных положительных измерений с точкой/запятой.
- Сон: среднее валидных длительностей. Поддерживаются «7 ч 15 мин», компактные варианты/сокращения с точками, часы с десятичной запятой/точкой, Ч:ММ, отдельные минуты. Число без единиц считается часами; допустимо 0–24 часа, некорректные строки пропускаются.

Карточки показывают число дней с данными из семи. Нет данных — «—», а не ноль. Средние рассчитываются до округления; округление только при отображении. В подсказках сохраняется дополнительная точность.

GET api/index.php?action=training-summaries&end=YYYY-MM-DD — новый read-only endpoint. Возвращает start/end и trainingSummaries с двумя скалярами на дату: distanceKm/movingSeconds. SQL извлекает лишь эти JSON-поля и версию, не загружает массивы сенсоров в PHP/браузер. Использует подготовленные запросы и действующую сессию: посетитель получает только опубликованные неудалённые записи, администратор — также активные черновики. Ни GPS, ни исходные FIT, ни приватные метаданные не выдаются. Поздние ответы прежней административной сессии игнорируются после выхода. Полные сенсорные данные по-прежнему загружаются только для выбранного отчёта/редактора.

## Расследование удаления/повторного создания

Проверены save/delete, archiveEntry/archiveTraining/storeTraining, транзакции, блокировка строки FOR UPDATE, версии, восстановление и история. Ошибка 1451 при физическом DELETE в phpMyAdmin ожидаема: FK training_sessions → diary_entries и training_history → entry_history защищают данные. В изолированной тестовой БД воспроизведена именно эта ошибка; такая операция откатывается. Отключать FK или вручную удалять историю нельзя.

Серверное мягкое удаление исправно: архивирует ревизию и FIT, устанавливает deleted_at, published=0 и увеличивает revision. Восстановление с revision=null архивирует удалённую ревизию, очищает deleted_at, увеличивает revision, применяет обычный флаг публикации и не возвращает старую FIT-сессию без нового вложения. Устаревшие версии активной записи по-прежнему получают 409. Изменять этот механизм не потребовалось.

Воспроизведена отдельная ошибка интерфейса: POST save успешно завершался, следующий GET entries падал, а редактор оставался открыт со старой revision. Повторное сохранение давало ложный для пользователя 409. Теперь подтверждённые сохранение/удаление закрывают редактор до обновления; ошибка чтения явно сообщает, что запись уже сохранена/удалена на сервере. Перед следующим редактированием загружаются свежие версии. При настоящем 409 форма остаётся открыта с несохранёнными полями. Неопределённый результат сетевой ошибки также требует свежего чтения перед новым открытием. Если дата в форме изменена, удаление другой выбранной календарной записи блокируется с понятным сообщением.

## Ручное обновление после проверки и слияния PR

1. Сохраните текущую резервную копию файлов и JSON-экспорт базы через администратора. Не выполняйте DELETE в phpMyAdmin.
2. Из одного и того же merged commit загрузите эти **пять** файлов. public/ в репозитории соответствует веб-корню домена в ISPmanager:

| Репозиторий | На сервере в веб-корне |
| --- | --- |
| public/weekly-analytics.js (новый) | weekly-analytics.js |
| public/api/index.php | api/index.php |
| public/app.js | app.js |
| public/styles.css | styles.css |
| public/index.html | index.html |

3. Сначала загрузите новый weekly-analytics.js и API, затем app.js/styles.css/index.html; лучше обновить комплект во время короткого окна обслуживания, чтобы не смешивать версии. Если исходный API содержит адаптированный путь require к private/bootstrap.php, сохраните действующий путь хостинга.
4. **Приватные файлы загружать не нужно. SQL-миграция не нужна.** Схема, конфигурация, private/config.php, секреты и существующие записи не меняются. Не загружайте tests/, attachments/ или локальную тестовую конфигурацию.
5. При отключённой проверке времени файлов OPcache очистите его средствами хостинга. Обновите страницу с очисткой браузерного кэша; index.html содержит новые версии ресурсов.
6. Проверьте анонимный режим и администратора: сегодня/текущий месяц, блок аналитики, пропуски/нули, переключение/перезагрузка, скрытые черновики после выхода. На отдельной тестовой записи проверьте сохранение, замену/удаление FIT, мягкое удаление, повторное создание без старого FIT. Проверьте существующие отчёты и графики.

Требования хостинга прежние: PHP 8.2+, PDO MySQL, MySQL 8/MariaDB с JSON_VALID/JSON_EXTRACT (текстовый JSON в существующих таблицах), сессии/HTTPS и доступ к существующей БД. Новых расширений, пакетов, cron или настроек не требуется.

## Проверки и изменённые файлы

Тесты используют только синтетические данные и loopback API с отдельной БД *_test. Нельзя запускать на production. Инструкции первоначальной подготовки тестовой БД/администратора остаются в README.md. Для повторного прогона требуется чистая тестовая БД; после tests/api.py сбросьте только тестовый auth_limits, так как тест намеренно исчерпывает лимит входа. Передайте DIARY_TEST_PASSWORD, при необходимости DIARY_TEST_URL и DIARY_TEST_PHP. Для теста конкурентного восстановления PHP_CLI_SERVER_WORKERS=4 (лишь локальный тестовый сервер).
